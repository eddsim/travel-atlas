# Travel Atlas 旅行手册规范

> 本规范以 `2026/09-24-phuket` 普吉岛手册为参考实现。后续新国家 / 城市旅行默认沿用同一套信息架构、视觉语言、交互和发布方式，再根据目的地内容做增减。

## 1. 目标

Travel Atlas 不是普通攻略页，而是一份“旅行当天真的会打开使用”的执行手册。设计优先级：

1. **打开就知道下一步做什么**：顶部展示“此刻关注”与倒计时。
2. **快速定位到某一天**：DAY1～DAYN + 待办 sticky Tab。
3. **交通 / 酒店 / 景点信息可立即执行**：地点支持导航和复制。
4. **弱网与离线可用**：核心内容访问过后可离线回看。
5. **公开页面不泄露敏感信息**：不展示订单号、证件号、手机号等隐私数据。
6. **全球可访问**：主域名 `travel.606858.xyz`，Cloudflare Workers + Static Assets 自动部署。

---

## 2. 目录与命名规范

每次旅行独立目录：

```text
public/trips/<YYYY>/<MM-DD>-<destination>/
├── index.html          # 旅行入口 / 增强层
├── base.html           # 主体内容与版式
├── trip-map.png        # 行程总览手绘地图（推荐 PNG/WebP）
└── assets/             # 可选：其他本地图片资源
```

示例：

```text
public/trips/2026/09-24-phuket/
public/trips/2026/11-03-tokyo/
public/trips/2027/01-18-osaka/
```

URL：

```text
https://travel.606858.xyz/<YYYY>/<MM-DD>-<destination>
```

目录 slug 使用英文小写、短横线分隔；日期必须以出发月日开头，方便排序。

## 3. 页面固定信息架构

默认按以下顺序排版。除非目的地明显不适用，否则不要随意打乱。

### 3.1 顶部 Hero

展示：

- 目的地中文 / 英文名
- 出发与返程日期
- 天数 / 晚数
- 同行人数（可选）
- 一句简短旅行定位，例如“海岛慢游 / 城市周末 / 自驾环线”

视觉：留白大、标题清晰、避免堆信息。

### 3.2 「此刻关注」

这是整页最高优先级模块。

必须包含：

- 下一事件标题
- 下一事件时间
- 实时倒计时：天 / 时 / 分 / 秒
- 时区必须按事件所在地计算，不能依赖查看者当前时区

当下一事件属于交通票务时，自动展示交通卡：

- 航班：航司、航班号、出发 / 到达机场、航站楼、当地时间、时区、飞行时长
- 高铁 / 火车：车次、出发站、到达站、发到时间、席别（如适合公开）
- 大巴：运营商 / 班次、上下车点、发到时间
- 船票：船班、码头、开船 / 抵达时间

禁止展示：订单号、身份证 / 护照号、座位号等不适合公开的信息。

### 3.3 顶部 Sticky Tab 导航

固定排列：

```text
DAY1 · 日期  DAY2 · 日期  ...  DAYN · 日期  待办
```

要求：

- 位于“此刻关注”下方
- 滚动后 sticky 吸顶
- 手机宽度不足时横向滑动，不换行
- 点击平滑滚动到对应 Day
- 滚动进入某一天时自动高亮对应 Tab
- `待办` 永远排在最后一天之后
- 锚点跳转必须预留顶部偏移，避免标题被 sticky 导航遮挡

### 3.4 行程总览地图

地图不是抽象路线海报，必须遵守：

1. **基于目的地真实地图轮廓 / 地理位置关系**。
2. 在真实底图基础上做“手绘旅行手册”风格，而不是改变地理关系。
3. 只突出本次实际相关地点，避免把整座城市 / 国家塞满。
4. DAY1～DAYN 路线按天分色，并配图例。
5. 不确定 / 天气条件路线使用虚线或弱化样式。
6. 酒店、机场 / 车站、核心景点需要有明显节点。

推荐视觉语言：

- 米白 / 纸张感背景
- 低饱和蓝色水域
- 低饱和绿 / 灰地形
- 深色手绘线条
- 每日路线采用不同但协调的颜色
- 少量插画，不喧宾夺主

**图片必须作为目录内静态资源引用，不使用 Base64 文本中转。**

### 3.5 已确认预订信息

只放“已经有订单 / 明确确认”的内容：

- 航班 / 火车 / 大巴 / 船票
- 酒店
- 接送机 / 租车
- 门票 / 活动

每张卡建议包含：

- 名称
- 日期 / 时间
- 地址
- 官方公开电话（如有必要）
- 状态：已确认 / 已出票 / 待确认

不要把尚未预订的活动写成“已确认”。

### 3.6 DAY1～DAYN 每日行程

每一天使用独立卡片，统一结构：

- DAY 标签 + 日期 + 星期
- 当日一句话主题
- 时间轴
- 地点 / 活动
- 交通时间估算
- 必要的 Plan B / 风险提示
- 当日 Google Maps 路线入口

原则：

- 航班 / 高铁等固定交通先锚定，再安排其他活动。
- 换酒店日必须留出退房、行李与入住缓冲。
- 返程日优先保证机场 / 车站时间，不塞远距离项目。
- 有营业时间 / 闭馆日 / 周末市集等强约束时，以它们决定当天顺序。
- 天气敏感活动必须有备选方案。

### 3.7 出发前准备 & 待办

必须是可勾选清单，并保存在浏览器 `localStorage`。

默认分组：

- 证件 / 入境
- 电子设备 / 网络
- 天气 / 目的地装备
- 出发前 24～48h
- 行程待办

交互要求：

- 每项独立 checkbox
- 勾选后弱化 + 删除线
- 顶部显示 `已完成 X / Y` 和进度条
- 刷新 / 关闭浏览器后状态仍保留
- 提供“清空勾选”
- localStorage key 必须带本次 trip slug，防止不同旅行互相污染

示例：

```text
travel-atlas:2026-09-24-phuket:prep-checklist:v1
```

待办 Tab 必须指向该模块。

### 3.8 实用提示

按目的地补充：

- 入境 / 签证 / 入境卡
- 现金 / 支付
- 插座 / 电压
- 网络 / eSIM
- 天气 / 穿衣
- 打车 / 公交
- 安全 / 紧急联系方式
- 小费 / 文化礼仪

政策、入境、交通规则等会变化的内容，发布前必须重新核实，避免永久写死。

## 4. 地点交互规范

所有地点类信息，包括：

- 景点
- 酒店
- 机场 / 车站 / 码头
- 餐厅
- 商场
- 夜市
- 集合点

默认应同时支持：

1. **Google Maps 导航 / 搜索**
2. **复制地点 / 地址按钮**

复制规则：

- 有明确街道地址：复制完整地址
- 景点 / 机场等更适合按 POI 搜索：复制英文 / 当地地图可识别名称
- 不复制订单号或个人信息

复制成功使用轻量 toast 提示，不弹阻塞式对话框。

## 5. 视觉设计规范

### 5.1 总体感觉

关键词：

`旅行杂志 / 手账 / 克制 / 轻量 / 温暖 / 移动端优先`

避免：

- 企业后台风
- 大量渐变霓虹
- 过多玻璃拟态
- 卡片层级过多
- 巨量图标和插画

### 5.2 卡片

- 圆角：中等偏大
- 轻边框 + 很弱的阴影
- 信息密度高但保持明显留白
- 一张卡只承担一个主题

### 5.3 Day 颜色

每个 Day 使用独立主题色，但饱和度保持一致。颜色同时用于：

- Sticky Tab 小圆点 / active 状态
- Day 卡片标识
- 总览地图当日路线

同一天在全页面必须保持同色语义。

### 5.4 深浅模式

根据系统 / 时间自动适配时：

- 保持文字对比度
- 地图图片本身不强制反色
- 地址复制、导航、checkbox 等交互必须仍清晰可见

---

## 6. 图片与静态资源规范

- 图片存放在当前 trip 目录或 `assets/` 下。
- 优先 `WebP` / 优化后的 `PNG` / `JPEG`。
- 不使用 Base64 txt 中转大图。
- 地图应保留可直接在 GitHub 预览的正常图片文件。
- 文件名使用英文小写短横线：`trip-map.png`、`hotel-map.webp`。
- 页面必须为图片写准确 `alt`。
- 大图应压缩到移动网络可接受的体积，同时保证地图文字清晰。

---

## 7. 移动端与弱网规范

页面优先为手机使用：

- 375～430px 宽度必须正常显示
- Sticky Tab 可横滑
- 按钮点击区域足够大
- 卡片不出现横向溢出
- 倒计时数字不换行错位
- 交通票卡在窄屏仍能读

弱网策略：

- HTML 短缓存，避免长期拿旧行程
- Cloudflare Edge 做适度缓存
- Service Worker / CacheStorage 保留最近成功打开的页面
- 第一次访问成功后，核心手册应能离线回看
- Google Maps 等第三方导航链接离线时不可用是允许的

---

## 8. 隐私与公开页面规范

因为页面是公开 URL，严禁展示：

- 护照号 / 身份证号
- 手机号（个人号码）
- 订单号 / PNR / 票号
- 房间号
- 银行 / 支付信息
- 二维码 / 条形码
- 任何可被用于冒领、改签或身份验证的字段

可以展示：

- 航班号 / 车次
- 公共酒店电话
- 酒店 / 景点公开地址
- 出发 / 到达时间
- 航站楼 / 车站
- 已确认状态

从订单截图提取信息时，默认先过滤敏感字段，再写入公开页面。

## 9. 新旅行制作流程

### Step 1：收集输入

至少需要：

- 目的地
- 出发 / 返程日期
- 航班 / 车次截图
- 酒店订单
- 想去的景点 / 活动
- 饮食、节奏、购物等偏好

后续可持续补：餐厅、活动票、接送、收藏攻略链接。

### Step 2：先建立“硬约束”

先锁定：

- 固定交通
- 酒店入住 / 退房
- 已出票门票
- 周几才有的活动
- 闭馆日

### Step 3：规划 Day 行程

以减少折返、保留缓冲和避免过度赶路为目标。

### Step 4：制作真实底图手绘总览

根据目的地真实地图位置关系绘制，并按 Day 分色。

### Step 5：生成页面

严格按照第 3 节的信息架构生成。

### Step 6：发布前检查

见文末验收清单。

### Step 7：提交 `main`

Cloudflare 自动构建部署；正式主域名统一使用：

```text
https://travel.606858.xyz
```

## 10. 发布验收清单

每次新旅行发布前至少检查：

- [ ] 日期、星期、时区正确
- [ ] 航班 / 车次时间与订单一致
- [ ] 酒店入住 / 退房日期正确
- [ ] 未把未预订项目写成已确认
- [ ] 所有 Day Tab 能跳转
- [ ] 最后有“待办” Tab，能跳到准备清单
- [ ] 滚动时当前 Day Tab 能正确高亮
- [ ] 所有关键地点有 Google Maps 入口
- [ ] 所有关键地点有复制按钮
- [ ] 总览地图基于真实地理位置关系
- [ ] 总览地图按 DAY 分色
- [ ] 地图图片文件可直接在 GitHub 预览
- [ ] localStorage 勾选刷新后仍保留
- [ ] 手机宽度无横向溢出
- [ ] 公开页面无隐私 / 订单敏感字段
- [ ] 首次打开后离线模式可回看核心内容
- [ ] 自定义域名路径可访问
